A Draw Carries Its Lineage

RE-2 split drawing into CR 121.2a's instruction and CR 121.1's draw, and made the second a decomposition of the first — the engine's first events that continue their parent's CR 614.5 applied set instead of starting a fresh one. This page walks four boards through the code as it stands, read by read, and ends in the table of where each read differs from the single DrawCard that RB left and RD never touched.

replacement/re-2-draw @ 3e09c72CR tmnt2026-09-11 Authority for the design: plans/replacement-architecture.md §3.2d, §4.1a and §9 (RE decision 1), with §11 items 18, 42, 53. Tests: mtgsim/tests/phase_re2_integration_test.rs.

The cycle in the middle is the whole page. execute_batch_inner reaches perform_action, which reaches execute_actions_inheriting, which reaches execute_batch_inner again — and the only thing that stops it is the set carried around that loop. The read tags below are the board board, the replacement registry registry, a player's answer player, and the applied set travelling down from the enclosing decision lineage.

Trace A — two Thought Reflections, one draw

Player 0 controls two Thought Reflections ("If you would draw a card, draw two cards instead" — not legendary, so a board can hold two) and resolves an instruction to draw one card. Its own ruling gives the answer: "if you have two Thought Reflections on the battlefield, you'll draw four times the original number. If you have three, you'll draw eight times."

CR 614.5 — "A replacement effect doesn't invoke itself repeatedly; it gets only one opportunity to affect an event or any modified events that may replace that event." The second clause is the whole of this page. A decomposed draw is such a modified event; a rider's draw is not.
  1. Primitive::DrawCards(Fixed(1)) proposes one instruction: execute_action(DrawCards { player: 0, n: 1, cause: Effect }). Before RE-2 this arm looped execute_action(DrawCard) n times and there was no instruction at all.
  2. execute_batch_inner(batch, inherited = {}). One member, one subject — subject_of(DrawCards) is Player(0) — so one group.
  3. apply_replacements, iteration 1: applied = inherited.clone() = {}. gather sweeps the battlefield board and reads each permanent's effective ability list; both Reflections offer their ReplacementDef, and pattern_watches asks (EventPattern::DrawCard, GameAction::DrawCards) — no arm matches. Neither applies. candidates.is_empty() → return ([(0, Some(DrawCards{1}))], {}).
  4. Phase 2. perform_action(DrawCards { n: 1 }, lineage = {}) lineage. The loop runs once: i == 0, so the inner takes the outer's cause (Effect), and execute_actions_inheriting([DrawCard { player: 0, cause: Effect }], ctx, {}) opens a batch that joins the enclosing one — the draws are the result of the instruction, which is §4.2's default.
  5. apply_replacements on the inner, applied = {}. Now pattern_watches matches (EventPattern::DrawCard { cause: None }, GameAction::DrawCard) for both Reflections; set_affects asks PlayerSet::You.contains(0, 0) board → both. Two candidates, both class Other; ordering_cannot_change_outcome is false (not all EnterWith, not all Multiplier on DealDamage), so ask_choose_replacement(player 0, …) player — the drawing player, which is the card's third ruling falling out of CR 616.1 rather than being coded. This is the only prompt a correct run makes.
  6. Say TR₁. applied.insert(TR₁). apply_rewrite takes the Instead(GameActionTemplate::DrawCards { n: 2, player: None }) arm: draw_recipient answers None → the affected player, 0. The substitute is DrawCards { player: 0, n: 2, cause: Effect } — the instruction, and it keeps the cause it replaced, because CR 614.6 makes it the original in modified form.
  7. Iteration 2 re-gathers against the substituted event (CR 616.1f). (EventPattern::DrawCard, GameAction::DrawCards) matches neither Reflection; (EventPattern::DrawCards, …) is nobody's here. No candidates → return ([(0, Some(DrawCards{2}))], {TR₁}).
  8. Phase 2, and the load-bearing line. perform_action(DrawCards { n: 2 }, lineage = {TR₁}) lineage. Two inners, each through execute_actions_inheriting(…, {TR₁}). Inner 0 takes the outer's cause; inner 1 is stamped Effect — the same here, since the outer was already Effect.
  9. Inner 0: applied = {TR₁}. gather offers both Reflections; the .filter(|c| c.def.exempt_from_614_5 || !applied.contains(&c.id)) leg drops TR₁. One candidate — so must_choose_among returns a list of one and nothing is asked. TR₂ applies → DrawCards { n: 2 }, applied = {TR₁, TR₂}.
  10. Its two inners inherit {TR₁, TR₂}; both Reflections are filtered; draw_card runs twice board — two ZoneChange { cause: Drawn } and two CardDrawn. Inner 1 of step 8 repeats the whole of steps 9–10. Four cards.
Without the inheritance, on the same board. Step 9 seeds applied = {} instead of {TR₁}. Both Reflections are candidates again, so must_choose_among returns two and the pipeline prompts — at depth two, before anything has had time to get deep. Each of the two inners then becomes an instruction of two, whose inners become instructions of two, and perform_action → execute_actions_inheriting → execute_batch_inner → perform_action recurses until the thread's stack is gone. Not a wrong number: STATUS_STACK_OVERFLOW, which aborts the whole test binary rather than one test.
The bound is in the provider, not the engine. A correct run makes exactly one CR 616.1 prompt — step 5 — because every later draw has one unapplied Reflection and the pipeline never prompts with fewer than two candidates. So the test primes a ScriptedDecisionProvider with exactly one expectation, and a broken lineage turns step 9 into ScriptedDecisionProvider: unexpected pick_n call. A red test with a message, at depth two, instead of a binary that never returns. No cap was added to the engine: CR 614.5's applied set is the termination argument, and a depth limit beside it would hide the bug this page exists for.

Three copies are 2³ by the same road, and they are a separate board rather than a flourish: two copies are also consistent with "each draw is doubled once per copy after the first", which three separate. three_thought_reflections_draw_eight makes exactly three prompts — the first draw offers three candidates, and each of that instruction's two inners offers two.

Trace B — Teferi's Ageless Insight beside a Thought Reflection, in the draw step

Player 0 controls both and takes their draw step. Teferi's reads "If you would draw a card except the first one you draw in each of your draw steps, draw two cards instead", and the answer is three cards. Four would mean a substituted instruction started fresh; two would mean the exception belonged to the instruction rather than to each draw.

Nothing counts cards drawn this step. DrawCause has two arms, the draw step is the engine's one TurnBased producer, and the stamping rule is three tokens of code in the outer's performer: if i == 0 { cause } else { DrawCause::Effect }. The exception is the shape of the event tree.
  1. process_draw_step proposes DrawCards { player: 0, n: 1, cause: TurnBased }. CR 504.1's turn-based action is "draw a card" — one "draw" of one card, and it proposes the outer like every other instruction so that Alms Collector's counting ruling has one rule to read rather than two shapes.
  2. Iteration 1 on the instruction: neither card's EventPattern::DrawCard matches a DrawCards. No candidates.
  3. perform_action(DrawCards { n: 1, cause: TurnBased }, {}): i == 0 → the inner is DrawCard { cause: TurnBased }.
  4. gather on that inner board: Thought Reflection's pattern is DrawCard { cause: None } → matches. Teferi's is DrawCard { cause: Some(Effect) } → Some(Effect) == TurnBased is false → does not match. One candidate, no prompt. TR applies.
  5. apply_rewrite: the substitute is DrawCards { n: 2, cause: TurnBased }. The cause travels — CR 614.6, the modified event occurs in the original's place, and this is still the draw step's instruction. applied = {TR}.
  6. perform_action(DrawCards { n: 2, cause: TurnBased }, {TR}) — and here the two inners are different:
    • i == 0 → DrawCard { cause: TurnBased }, inherited {TR}. TR is filtered; Teferi does not match TurnBased. Card 1, undoubled — the one the card excepts.
    • i == 1 → DrawCard { cause: Effect }, inherited {TR}. TR filtered; Teferi matches. One candidate, no prompt.
  7. Teferi's substitute is DrawCards { n: 2, cause: Effect }, applied = {TR, Teferi}. Its first inner is Effect too, because the stamp copies the outer's cause and the outer is no longer the draw step's. Both inners are filtered against both effects. Cards 2 and 3.
Read step 7 twice. "The first inner carries the outer's cause" is not "the first inner is always TurnBased". Once a doubling has been applied to an Effect instruction, its first card is an Effect card too — which is why the recursion stops at three rather than producing a fresh excepted card at every level. The rule reads as one sentence and is really two: the exception belongs to the draw step's first draw, and the tree is what remembers which one that was.

The two halves alone are the boards either side of this one. teferi_excepts_the_draw_steps_first_card takes a draw step with Teferi and nothing else: one card, undoubled. teferi_doubles_a_draw_that_is_not_the_draw_steps takes the same step and then a spell: three cards, one from the step and two from the spell.

Trace C — Alms Collector, in both encodings

Player 0 controls Alms Collector ("If an opponent would draw two or more cards, instead you and that player each draw a card"); player 1 controls Thought Reflection and resolves an instruction to draw two.

This is the trace §9 named, and it did not survive the writing of the test. The section sized the card as Prevent with a rider of two draws, on §3.2d's rule that heterogeneous multiplicity goes in then. Both encodings are walked below because the difference between them is a printed ruling, and because only one of them terminates.

Alms Collector's second ruling — "Once a replacement effect has been applied to an event, it can't be applied again to the resulting events. For example, once Alms Collector's replacement effect has modified the effect of a player's Divination, Thought Reflection can double that player's resulting card draw without Alms Collector's replacement effect applying again."

C — as shipped: Instead(DrawCards { n: 1 }) plus one rider

  1. Primitive::DrawCards(Fixed(2)) for player 1 → DrawCards { player: 1, n: 2, cause: Effect }.
  2. Iteration 1. pattern_watches asks (EventPattern::DrawCards { at_least: Some(2) }, GameAction::DrawCards { n: 2 }) → 2 >= 2 → matches; set_affects asks PlayerSet::Opponents.contains(0, 1) board → yes. Thought Reflection watches a DrawCard and is not offered. One candidate, no prompt.
  3. apply_rewrite: Instead(DrawCards { n: 1, player: None }) on a DrawCards — the arm's second leg, an instruction rewritten into a smaller instruction. The affected player keeps the draw: DrawCards { player: 1, n: 1, cause: Effect }. applied = {Alms}. One Rider is queued for "you draw a card", subject Player(1).
  4. Iteration 2: at_least: Some(2) against n: 1 → no. Return ([(0, Some(DrawCards{1}))], {Alms}).
  5. perform_action(DrawCards { n: 1 }, lineage = {Alms}) lineage → one inner, inherited {Alms}. Thought Reflection matches and applies → DrawCards { n: 2 }, applied = {Alms, TR}.
  6. Iteration on the substituted instruction: Alms Collector's pattern matches again (n: 2, still an opponent's) — and the applied filter drops it. That is the ruling, and it is the only place in the trace where it is enforced. No candidates.
  7. Two inners inherit {Alms, TR}; both are filtered; player 1 draws 2.
  8. Phase 3: resolve_rider proposes the controller's draw through resolve_effect → a fresh batch and a fresh applied set (§3.2d containment). Thought Reflection is player 1's and PlayerSet::You does not contain player 0, so nothing applies. Player 0 draws 1. Three cards, and it terminates.

C′ — as sized: Prevent plus two riders

  1. Iteration 1 is identical: Alms Collector matches the instruction of two.
  2. apply_rewrite: Prevent → the event is None. Two riders queued — "you draw a card" and "that player draws a card". The applied set {Alms} is returned, and nothing is left to hand it to: there is no surviving event, so perform_action never runs and the lineage dies here.
  3. Phase 3, rider 2: player 1 draws one, through resolve_effect → execute_action → a fresh applied set.
  4. The inner DrawCard { player: 1 } meets Thought Reflection → DrawCards { n: 2 }, applied = {TR}.
  5. Re-gather: Alms Collector matches n: 2, and {TR} does not contain it. It applies again — the thing its ruling says cannot happen. Prevent, two more riders.
  6. Rider 2 of those gives player 1 one draw, with a fresh set again. Steps 4–5 repeat. Each cycle hands player 0 a card and player 1 a doubled draw, and neither effect is ever filtered because every rider starts over.
What C′ actually does. In the rules it is CR 104.4b — a loop of mandatory actions with no way to stop, so the game is a draw — and CR 731 loop detection is explicitly out of this phase's scope. In the engine it is recursion through resolve_rider → resolve_effect → execute_action → apply_replacements until the stack is gone. The first run of alms_collector_does_not_apply_again_to_the_draws_it_produced reported STATUS_STACK_OVERFLOW and took the test binary with it.
The rule both "and" cards needed, and it is CR 614.5's second clause read as an instruction to the card author. An effect's one opportunity covers "any modified events that may replace that event" — which is what the rewrite outputs, and not what a rider proposes. So split a printed "instead X and Y" by asking which half CR 614.5 has to cover, and put that half in the rewrite. Notion Thief's is the draw with a new subject; Alms Collector's is the same draw with a smaller count — §3.2d's own homogeneous case, hiding inside a heterogeneous sentence. Each card's remainder is a different player's draw, which nothing watches twice.

Trace D — three Notion Thieves

Players 0, 1 and 2 each control a Notion Thief; player 0 resolves an instruction to draw one. The ruling is a procedure: "that player chooses one of the applicable Notion Thief effects to apply. Then the player whose Notion Thief's effect was chosen repeats this process among the remaining Notion Thief effects … Each effect can be applied to the card draw only once this way."

Nothing in the engine implements that procedure. Every clause of it is a consequence of two facts already on the page: a substitution may move the event's subject, and CR 616.1's chooser is derived from the event rather than captured.

  1. DrawCards { player: 0, n: 1, cause: Effect } → no candidate → one inner DrawCard { player: 0, cause: Effect }, inherited {}.
  2. gather board: each Thief's set_affects asks PlayerSet::Opponents.contains(controller, 0), so Thief₀ does not apply — nobody is their own opponent — and Thief₁ and Thief₂ do. Two candidates, in battlefield_ids_ordered (CR 613.7 timestamp) order. chooser_for(DrawCard { player: 0 }) → Player(0). Player 0 is asked player — the ruling's first clause.
  3. Say Thief₁. apply_rewrite takes Instead(DrawCards { n: 1, player: Some(PlayerRef::You) }); draw_recipient answers chosen.controller = 1. The event becomes DrawCards { player: 1, n: 1, cause: Effect }. applied = {Thief₁}. The subject moved and the lineage did not.
  4. Iteration 2 on the substituted instruction: every Thief's pattern is DrawCard, so nothing matches a DrawCards. Return ([(0, Some(DrawCards{1, player: 1}))], {Thief₁}).
  5. perform_action(…, lineage = {Thief₁}) lineage → DrawCard { player: 1 }, inherited {Thief₁}.
  6. gather: Thief₀ and Thief₂ apply (player 1 is an opponent of both); Thief₁ is filtered by the applied set. Two candidates. chooser_for reads the event, which is now about player 1 — so player 1 is asked. That is the ruling's "the player whose Notion Thief's effect was chosen repeats this process", and it is one line of subject_of rather than a rule.
  7. Say Thief₀. The event becomes DrawCards { player: 0, n: 1 }, applied = {Thief₁, Thief₀} → one inner DrawCard { player: 0 }, inherited both.
  8. gather: Thief₁ is filtered, Thief₀ is filtered, and Thief₀ would not apply to its own controller's draw anyway. Thief₂ alone — one candidate, so nothing is asked. The event becomes player 2's.
  9. Its inner inherits {Thief₀, Thief₁, Thief₂}. Nothing applies. draw_card(2) board. One card, three hops, each effect applied once.
Two players is the ruling's own worked example and a different shape. With one Thief each, no step ever has two candidates — a Thief never watches its own controller's draw — so two_notion_thieves_hand_the_draw_across_the_table_and_back asserts zero prompts and the draw comes home: player 1's Thief takes it to player 0, player 0's takes it back, both are spent, player 1 draws. "It really will be that player who draws a card." With three, the draw does not come home — it lands on the controller of the last Thief to apply, which is player 2 above. Both are the same mechanism and only one of them is intuitive, which is why the test asserts the unintuitive one.

What RE-2 changed, trace by trace — and what is still open

A is the phase in one board: inherited stopped being an empty set with a doc comment and became the thing that terminates the loop. The engine gained no cap and wants none — CR 614.5's applied set is the argument, and a depth limit beside it would answer the wrong question loudly.

B is what a well-chosen enum arm buys. DrawCause is two variants and one if in a performer, and it replaces the per-player, per-step counter that "except the first one you draw in each of your draw steps" reads like it needs. The rule that makes it work is that a substituted instruction keeps the cause it replaced, which is CR 614.6 and not a special case.

C is the rulings pass doing design work for the third time (after Furnace of Rath's and Notion Thief's), and the first time it has overturned a correction made the same day. Worth keeping for the shape rather than the card: both mis-filings put an effect's whole output in then, both produce a loop rather than a wrong number, and both loops are the kind CR 731 would have to catch and does not.

D is the argument for deriving rather than capturing. Every clause of a three-sentence ruling falls out of subject_of being asked per iteration and chooser_for being asked of the event — neither of which RE-2 wrote.

Open, each with a dated line in codebase-state.md: CR 121.2c orders two players' draws and no Effect arm can express it, so Alms Collector's two draws come out affected-player-first (item 122); CR 121.6c has no producer, because nothing can name the card an earlier instruction drew, and ATOM-614.11b-001 stays uncovered for that reason (123). GameActionTemplate::DrawCards refuses PlayerRef::Owner and Opponent rather than guessing — a draw's subject is a player, so there is no object to own and no rule that says who "an opponent" is — and each is one printed card away from an arm. RE-3 is the next PR and inherits the template arm it extends; plans/replacement-architecture.md §9 has the order.
