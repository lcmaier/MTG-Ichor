A Decision Is Per Subject

RD-2 changed the unit of the CR 616.1 loop — from the batch member to the pair (batch, subject) — moved the spending of a use to after its application, and gave CR 615.7's allocation a prompt. This page walks four boards through the code as it stands, read by read, and ends in the table of where each read differs from the loop RD-1 left.

Every step below names the function and what it read. The read tags are the board board, the replacement registry registry, a player's answer player, and batch-scoped state on GameState state.

Trace A — two shield counters under two blockers

§11 item 15's board, and the regression for the whole PR. Player 0's 3/3 with two shield counters attacks; player 1 blocks with two 2/2s. CR 510.2 makes all combat damage one event, so the four damage assignments arrive as one batch.

CR 122.1c — "One or more shield counters on a permanent create a single replacement effect and a single prevention effect … If damage would be dealt to this permanent, prevent that damage and remove a shield counter from it." The Streets of New Capenna release notes: two creatures dealing combat damage to it at once, "that damage is prevented and only one shield counter is removed."
  1. process_combat_damage(dp, false) → assign_combat_damage walks battlefield_ordered board. The attacker has two blockers, so ask_choose_attacker_damage_assignment asks player 0 player: 2 to the first blocker, 1 to the second. Four assignments, in battlefield order: first→attacker 2, second→attacker 2, attacker→first 2, attacker→second 1.
  2. apply_combat_damage → execute_actions opens one batch id and calls execute_batch_inner.
  3. apnap_batch_order: chooser_for reads each subject's controller board. Members 0 and 1 are about the attacker (player 0, the active player); members 2 and 3 are about player 1's blockers. Order [0, 1, 2, 3].
  4. Grouping. subject_of buckets the ordered members: {attacker: [0, 1]}, {first: [2]}, {second: [3]}. Three groups, three loops — where the per-member loop ran four.
  5. apply_replacements(group {attacker}), iteration 1. never_happens: neither 2 is 0. EntryFrame::new for a DealDamage builds nothing. Per member, is_prohibited(Query::Event) board — no restriction sweep applies — then gather board: the fast path opens because any_replacement_counter sees the shield counters; counter_replacements(attacker) synthesizes CR 122.1c's two effects and pattern_watches keeps the prevention half (EventPattern::DealDamage) and drops the replacement half (Destroy). Both members gather the same instance — Counter(attacker, Shield, Prevention) — and the union keyed by ReplacementInstanceId holds one Candidate with members: [0, 1].
  6. must_choose_among: one candidate, class Other. chooser_for answers player 0 for the whole group. One candidate, so nothing is asked and ordering_cannot_change_outcome is not consulted.
  7. Not optional. applied.insert(Counter(attacker, Shield, Prevention)) — one slot in one applied set, for both members.
  8. next_damage_shares is skipped: the rewrite is Prevent, not PreventRemaining.
  9. Apply per member. apply_rewrite on member 0: Prevent → (None, Applied { took_effect: true, prevented: 0 }). Member 1: the same. replaced_amount sums to Some(4).
  10. One rider. then is remove_one_counter(Shield); one Rider { subject: attacker, replaced_amount: Some(4), prevented: 0 } is pushed — not two.
  11. consume_use(outcome): counter-derived, so nothing — the counter removal is the rider (CR 122.1c makes it the substituted event or the rider, never bookkeeping).
  12. Iteration 2: both members are None; apply_replacements returns [(0, None), (1, None)].
  13. Groups {first} and {second}: gather finds nothing (no counters on the blockers, an empty registry) and each returns its member unchanged.
  14. Phase 2 performs members 2 and 3: 2 marked on the first blocker, 1 on the second board. Phase 3 runs the one rider: resolve_rider proposes RemoveCounters { Shield, 1 } through execute_action — its own batch of one, a fresh applied set — and the attacker goes from two counters to one. Damage marked on it: 0.
The per-member loop, on the same board. Member 0's loop gathered the counter effect, applied it, queued a rider, returned None. Member 1's loop began with a fresh applied set, gathered the same effect — still two counters on the board, since riders run in phase 3 — applied it again, queued a second rider. Phase 3 then removed two counters. Both damages were prevented either way, which is why the bug was invisible with one counter: the second rider removed nothing, and the answer was accidentally right.

A′ — the same board with a first striker

Replace the second blocker with Knight of Meadowgrain (first strike, in the pool). CR 510.4 makes two combat damage steps.

  1. process_combat_damage(dp, true): assign_combat_damage with first_strike_only keeps only the Knight → a batch of one: knight→attacker 2.
  2. One group {attacker: [0]}. The counter's prevention applies, one rider, one counter removed at phase 3. The Knight is recorded in dealt_first_strike_damage.
  3. process_combat_damage(dp, false): the regular step's batch — first→attacker 2, attacker→first 2, attacker→knight 1 (should_deal_damage_this_step excludes the Knight). Player 0 is asked the 2/1 split once more player.
  4. Group {attacker: [0]} again — a new batch, a new group, a new applied set. The counter effect (one counter left) applies once more; the second counter goes.
What A and A′ prove together: the key is (batch, subject) and not (turn, subject). Same creature, same two blockers, same turn; one batch spends one counter, two batches spend two — which is exactly what the CR's two-step rule says should happen.

Trace B — Furnace of Rath beside Mending Hands, 5 damage, both orders

Furnace of Rath's own ruling, at last with a printed prevention to order against: "you can choose whether to prevent 4 and then double the remaining 1, or double to 10 and then prevent 4." Player 0 controls Furnace; player 1 cast Mending Hands on themself; a 5-damage bolt from player 0's creature.

  1. The row. resolve_effect → resolve_primitive(CreateReplacement). The recipient is Target(Any) and the resolved target is Player(1), so the authored empty Fixed is filled: one RegisteredReplacementEffect with affected_players: Fixed([1]), uses: NextDamage(4), rewrite: Amount(PreventRemaining), duration: UntilEndOfTurn, source the spell, controller 1, targets: [Player(1)] registry.
  2. execute_action(DealDamage 5 → Player 1): a batch of one, a group of one.
  3. Iteration 1, gather: has_static_source is true — Furnace is in replacement_ability_sources — so the sweep reads Furnace's effective abilities board; set_affects asks PlayerSet::Everyone.contains(0, 1) → yes. Then the registry registry: Mending Hands' row, Fixed([1]).contains(1) → yes. Two candidates, sweep first: [Furnace (StaticAbility), Mending Hands (Registered)].
  4. must_choose_among: both Other. ordering_cannot_change_outcome: not all multipliers — one member is PreventRemaining — so false; this choice is real (it is the ruling).
  5. ask_choose_replacement(player 1, sources [Furnace, Mending Hands]) player.

Order 1 — the shield first (index 1):

  1. next_damage_shares: the rewrite is PreventRemaining on NextDamage(4). One applicable member, no later members → one bucket → [min(4, 5)] = [4], nothing asked, nothing stored.
  2. apply_rewrite(share 4): PreventRemaining.capped(4) = PreventUpTo(4); prevented 4, after 1, took_effect. No rider on Mending Hands.
  3. consume_use, after the application: spend_next_damage(row, 4) → 0 → the row is removed registry.
  4. Iteration 2 on the 1-damage event: gather finds Furnace only (the row is gone; Furnace is not yet in the applied set). One candidate, forced: ×2 → 2.
  5. Iteration 3: Furnace is in the applied set; no candidates. Phase 2 performs 2 damage → the contained LoseLife → player 1 at 18.

Order 2 — Furnace first (index 0):

  1. Iteration 1 applies Multiplier(2): 5 → 10. took_effect; Furnace is Static, nothing to spend.
  2. Iteration 2: Mending Hands alone (Furnace applied). next_damage_shares → [min(4, 10)] = [4]; PreventUpTo(4) on 10 → prevented 4, after 6.
  3. spend_next_damage(row, 4) → removed. Iteration 3: nothing. Player 1 at 14.
Either order spends the count by exactly 4, because the spend happens after the application and reads what it did — not because 4 happened to be the count. Order 1 prevents 4 of 5; order 2 prevents 4 of 10. Under the old order of operations the count would have had to be reduced before anyone knew how much of it the event could take.

Trace C — a count of 3 under sources of 2 and 4

ATOM-615.7-002's board. Player 1's Mending Hands is first brought from 4 to 3 by a 1-damage ping; then player 0's two attackers, powers 2 and 4, connect at once.

CR 615.7 — "If damage would be dealt to the shielded permanent or player by two or more applicable sources at the same time, the player or the controller of the permanent chooses which damage the shield prevents." And its last sentence: "such effects count only the amount of damage; the number of events or sources dealing it doesn't matter."
  1. The ping. A batch of one; next_damage_shares → [min(4, 1)] = [1]; prevented 1, after 0. spend_next_damage(row, 1) edits the row in place through update_rows — same id, NextDamage(3) registry. Iteration 2: never_happens drops the 0 (CR 614.7a). Nothing is dealt, nothing is announced.
  2. Combat. apply_combat_damage → a batch of two: A→Player 1: 2, B→Player 1: 4, in battlefield order. Both choosers are player 1; one group {Player 1: [0, 1]}.
  3. Iteration 1, gather per member registry: the row applies to both → one Candidate, members: [0, 1]. One candidate, so no ChooseReplacementEffect prompt — CR 616.1 has nothing to order.
  4. next_damage_shares: here = [(0, A, 2), (1, B, 4)]. prevention_allocations.shares_for(row) state → none yet. later is empty (no other group). Two buckets; chooser_for on each member board → player 1 and player 1, one chooser. record_prevention_allocation ticks the reachability counter.
  5. ask_allocate_next_damage(player 1, source Mending Hands, remaining 3, [(A, 2), (B, 4)]) player: total min(3, 6) = 3, mins [0, 0], maxs [2, 4]. The scripted answer is [2, 1] in one run and [0, 3] in the other; validate_allocation checks the sum and the caps.
  6. The answer is pushed onto GameState.prevention_allocations state as (row, [(0, 2), (1, 1)]) — before anything is applied, so a fork at any later prompt in this batch would see it (item 40).
  7. Apply per member, with its share. Member 0: capped(2) → prevented 2, after 0. Member 1: capped(1) → prevented 1, after 3. outcome.prevented = 3, took_effect.
  8. consume_use: spend_next_damage(row, 3) → 0 → removed registry.
  9. Iteration 2: member 0 is a 0 and never_happens drops it; member 1 gathers nothing. Return [(0, None), (1, Some(3))]. Phase 2: DamageDealt(B, 3), player 1 at 17. With [0, 3]: DamageDealt(A, 2) and DamageDealt(B, 1) — still 17.
The per-member loop, on the same board. Member 0's loop would prevent min(3, 2) = 2 and spend 2; member 1's would prevent min(1, 4) = 1. The total is the same 3 — and the choice CR 615.7 gives the shielded player never exists. That is the "silent wrong choice" §9's RD decision 3 says a phase must not open: first-come allocation, with no prompt to show it happened.

C′ — the multi-subject instance

The allocation is per instance, not per group. a_count_spanning_you_and_your_permanents_is_allocated_once_divine_deflection_waits_on_variable puts a count of 3 over "you and permanents you control" under attacker A (2, unblocked) and attacker B (4, blocked by your 5/5). Three members, three subjects; the count applies to two of them.

  1. Groups in APNAP order: {B: [wall→B 5]} (player 0's creature, active player first), then {Player 1: [A→you 2]}, then {wall: [B→wall 4]}. Group B has no candidates.
  2. Group {Player 1} chooses the count (forced). next_damage_shares: here = [(1, A, 2)]; no stored shares; the later members board: B→wall 4 is DealDamage and applies_to says yes (the wall is player 1's, the row's Filter is ByController(You)). Two buckets across two subjects; both choosers are player 1.
  3. ask_allocate_next_damage over [(A, 2), (B, 4)], total 3 player → [1, 2], stored as (row, [(1, 1), (2, 2)]) state. This group's share: [1]. Prevent 1 of 2; spend 1 → NextDamage(2).
  4. Group {wall}: the row is re-gathered with NextDamage(2); next_damage_shares finds stored shares state and returns [min(2, 4, 2)] = [2] — no second prompt. Prevent 2 of 4; spend 2 → removed.
  5. Player 1 at 19, the wall marked 2, B marked 5 (the wall's own damage is nobody's business). One prompt, one instance, three subjects.

Trace D — nothing was consumed, and why

Two boards where the count ends untouched, for two different reasons the code now keeps apart.

D — Safe Passage beside Mending Hands, 3 damage, both orders

  1. Rows, in registration order registry: Safe Passage — Filter {creatures you control} + PlayerSet::You, Prevent, Static; Mending Hands — Fixed([1]), NextDamage(4).
  2. Iteration 1: both apply to damage to player 1 (You.contains(1, 1); Fixed([1])). Two candidates, not order-invariant → ask_choose_replacement player.
  3. Safe Passage first (index 0): Prevent → None, took_effect; consume_use on a Static spends nothing. Iteration 2: no live member; return. Mending Hands was never chosen: its row still says NextDamage(4), and CR 614.5's opportunity for it never arose because the event stopped existing first.
  4. Mending Hands first (index 1): shares [min(4, 3)] = [3]; prevent 3, after 0; spend_next_damage(row, 3) → NextDamage(1). Iteration 2: never_happens drops the 0 before Safe Passage is gathered again. Player 1 at 20 either way; the count reads 4 or 1, and only the second spent anything — because only the second prevented anything.

D′ — chosen, and did nothing

Dark Sphere's shape (RD-3's card), as a fixture: a Once row, PreventHalf(Down), with a rider "you gain that much life", chosen against 1 damage.

CR 609.7b — "… If for any reason the shield prevents no damage or replaces no damage, the shield isn't used up."
  1. One candidate, forced. apply_rewrite: PreventHalf(Down).prevented(1) = 0, apply(1) = 1; so Applied { took_effect: false, prevented: 0 } — the event came out as it went in.
  2. The rider is queued regardless (CR 615.12's unconditional-once-queued), with prevented: 0.
  3. consume_use: Once and !took_effect → return without removing the row registry. Under the old order the row was removed on being chosen, one line before anyone computed that it would do nothing.
  4. Phase 2 deals 1 (player 1 at 19). Phase 3: resolve_rider builds a context with damage_prevented: Some(0); GainLife(DamagePrevented) evaluates to 0 and never_happens drops it (CR 119.10) — no LifeChanged. The next 5 damage meets the same row: prevents 2, gains 2, and then the row goes.

What RD-2 changed, trace by trace — and what is still open

A is the change of unit: execute_batch_inner groups by subject_of, and one applied set per group is what makes CR 122.1c's ruling come out right without making Kalitas's come out wrong. A′ is the proof that the batch scopes the group, which is the fact CR 510.4 hands the engine for free once the unit is right.

B is decision 7 made observable: because the spend follows the application, "prevent 4 then double" and "double then prevent 4" both cost the count 4 — the number the application reports, not the number the row started with.

C is decision 3's other half: CR 615.7's choice exists only when several sources meet one count at once, it is the affected side's, it is asked once per instance over every member the instance applies to, and its answer is state a fork must see. C′ is the same rule reaching across subjects, which is the shape Divine Deflection and Harm's Way will need and RD-2 tests through a fixture.

D separates two reasons for an untouched count — never chosen versus chosen and did nothing — which the old loop could not have told apart because it spent the use before it knew. That separation is also why §11 item 30's re-ask came back "no move": NextDamage(remaining) on the row is a number a test can read, not an absence.

Open, each with a dated line in codebase-state.md: the row's targets have no reader until Divine Deflection's recipient leaf (item 90); PreventUpTo waits for RD-3's source predicate to get a printed producer (91); a count spanning subjects with two choosers is refused rather than answered (92); a later group's doubling ahead of a stored share moves the member, not the share (93); Kitsune Palliator's each-player recipient does not exist (94). RD-3 inherits the group form with candidates that already carry per-member applicability, which is the seam its source predicates need — plans/handoffs/rd.md says what else.
