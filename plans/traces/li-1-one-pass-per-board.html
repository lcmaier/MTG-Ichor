One Pass Per Board

Until LI-1 the layer system walked one object through the ten layers, and every read it made of another object was answered as that object stood at the end of the previous layer. CR 613 describes a pass per layer over the whole board, in which each thing applied can see everything applied earlier in the same layer. This page is the difference, walked one call at a time: the pooled board that broke the old walk, the look-ahead for an entering permanent, and a card in a graveyard that no row can reach — plus the struct that holds a pass, field by field, because the review asked for it.

The map

One entry point, three routes, one loop. compute_characteristics is what every oracle wrapper calls; on a memo miss it asks membership which route the object takes. A permanent takes the pass: Board::seed lays out every member's printed characteristics, and then, layer by layer, applications_in_layer collects what the layer applies and apply_layer applies it in order. Every pink node is new; every read inside the loop goes through Board::frame_of.

Board, field by field

The big picture first. A frame is one object's characteristics at some point in the walk: its types, colors, abilities, power and toughness, controller — the thing every oracle wrapper reads and the thing continuous effects modify. The walk starts every frame at the printed values and pushes it through the ten layers; at the end of the walk the frame is the object's effective characteristics, and that is what the memo stores and what is_creature or get_effective_abilities returns. The working set is the set of objects whose frames a pass builds together — every object some registry row could reach — because CR 613 says each layer is applied to all of them at once, and an application to one of them (Humility stripping the Hierophants) must be visible when the next application looks (the Hierophants' grant checking whether it still exists). A Board is that set of frames while a pass is building them.

There are two ways to hold a Board. Live: a pass is running, and every member's frame is in the map, half-built. Settled (Board::settled()): no pass is running and the map is empty; it exists only so that a non-member's walk — a card in a graveyard with a CDA that counts the battlefield — can read a permanent's frame through the same frame_of call, which in that mode goes to the memo (the finished frames a pass already stored) instead of a live map. Same function, same evaluators, two sources of truth: mid-pass frames, or finished ones. It is built by Board::seed, mutated by apply_one, and consumed by into_frames (every member's frame goes to the memo) or take (one frame is kept, the rest dropped).

Why "accessor 1" and "accessor 2". The names are RC-4's (replacement-architecture.md §5d), and the rule behind them is CR 614.12: to decide an enters-the-battlefield replacement, look at the permanent as it would exist on the battlefield. The walk reads concrete game state in exactly two places — the entity (controller, counters, status) and the registry's rows — so RC-4 routed those two reads through one accessor each, and a look-ahead for an entering object perturbs just those two answers (the would-be entity, the would-be rows) without cloning the game. The pass keeps both: Board::entity is accessor 1 and rows_in_layer is accessor 2.

Two functions beside the struct do the work. applications_in_layer builds the layer's list — every member's CDAs at that layer (read off its live ability list, CR 613.3), the registry's rows for the layer plus the look-ahead's would-be rows (CR 613.7), keyword counters at layer 6 and P/T counters at 7c (CR 613.7c) — and sorts it once on (is_cda desc, timestamp, tiebreak). apply_one applies one entry: existence, then targets, then for each target resolve (make the reads) and apply (make the write).

The entry's three routes

membership(game, id) answers one question: can any registry row reach this object? It reads the AffectedSet variants rather than a list. A Filter or Host row reaches the battlefield; a SourceOnly row reaches its source, a permanent; a Fixed row names what it names, anywhere. So:

What LI-1 changed, and what it did not

Changed

  1. The unit of computation is a board, not an object. A memo miss for any permanent computes every permanent and stores them all; Layer walks fell 2,425 → 328 per 50 games and Board walks (236) is most of what is left.
  2. Every read of another object is live. Trace A's step 10 is the whole phase. The descending-ceiling termination argument went with it (§5.2); the canary still overflows a version that re-enters the pass.
  3. Counters are applications. Keyword counters already interleaved with rows by timestamp; P/T counters now do too.
  4. CR 613.6 locks a set, not a per-object mark.
  5. A layer-6 static granted by resolution applies — the assert in register_granted_static_effects admits layer 6 now (Rune of Flight's shape).

Not changed

  1. The order within a layer. Still CR 613.3 then timestamp; CR 613.8's dependency ordering is LI-2. Trace A is right only because Humility's timestamp is earlier — the Blood Moon boards in item 8 are still wrong today.
  2. What a filter reads, what an amount means, how a modification writes. permanent_matches_filter, evaluate_amount and the per-arm writes are the old code, split into a read step and a write step.
  3. The look-ahead's contract (CR 614.12, §5b): the entering object is visible to filters, invisible to counts, and its own rows reach only itself.
  4. The memo's key: one epoch, no finer key (§12 "7a"). The pass's output is what the memo stores, as that section said it would be.
  5. Determinism. Three serial runs per pool are byte-identical outside the timing block. One game in forty differs from main on each pool because the answer on trace A's board changed, not because anything varies between runs.

How the three systems meet

The layer system answers one question: what is this object right now. Continuous effects are its input — registry rows written when a permanent with a static ability enters (register_static_effects) or when a spell resolves (a pump, a control change), each row saying which layer it belongs to, whom it affects and what it does. The pass reads those rows and produces frames; the memo keeps the frames until something writes a walk input and bumps the epoch.

The replacement pipeline (CR 614–616) sits somewhere else entirely: between a proposed mutation and its performance, inside execute_actions. It does not modify characteristics; it modifies events. But it asks the layer system three kinds of question. Which replacement abilities exist is read off objects' effective ability lists (so Humility stripping "enters tapped" from a land is the walk's doing, not the pipeline's). Whether a "can't" applies is read the same way (CR 614.17). And for a permanent that is entering, CR 614.12 says to look at it as it would exist on the battlefield — that is compute_as_entering, trace B, a pass with the entering object added. When the pipeline is done deciding, the performer mutates the state, the epoch bumps, and the next question about any permanent runs a fresh pass.

So the direction of dependence is one way. The pipeline and the "can't" predicate consume frames; the layer system consumes rows and the raw state; nothing in the layer system proposes an event. CR 613.8 (LI-2) changes only the order in which rows are applied inside a layer. Triggered abilities (item 6) will consume the performed-event stream the pipeline leaves behind, and will read frames the same way the pipeline does — which is why item 7 precedes item 6: the frame a trigger's intervening-if evaluates against is the pass's output.
