A Multiplier Is Read Where Its Trigger Looks

TR-5g counts how many times a matched trigger triggers (CR 603.2d). The count could only be right by reading multipliers through the same machinery the dispatcher already used to read triggers: three kinds of ability list, and a rule for which list answers which arm. This page walks that machinery on three traced boards, so the functions the review asked about (lists_before, push_live_candidates, AnsweredArms::admits, trigger_multiplier_candidates) have a board under each.

The map

A window is the records one batch performed, read at the batch's close (TR-1's page). A candidate is one object's ability list as the dispatcher reads it, and an object can be more than one candidate: its list now, and the list it had before the event. CR 603.10 says which: an arm that looks back (a leaving, a control change, a countered spell, a loss) reads the abilities that existed immediately before the event; every other arm reads the board after it. Each trace is one way a list from before comes to exist.

AnsweredArms is the answer to one question per (list, record): which arms may this list answer? admits(arm) applies it to one arm. Before TR-5g the test lived inline in match_def; the count needs the same test for a multiplier's list ("is this multiplier on the board the doubled arm reads?"), so it became one method both call. A second copy is exactly how the two would drift.

Why the count gathers multipliers instead of looking at the triggers. A trigger does not know whether it is doubled; the doubling is a static ability of some other permanent (Panharmonicon, Gandalf, Teysa). So the count is a pass over the matches the dispatcher already made, asking each against every permanent that might carry a multiplier. trigger_multiplier_candidates finds those permanents and reads each the way the dispatcher reads a trigger's source. A multiplier has no registry row (it applies to no object, CR 613 does not reach it), so trigger_multiplier_sources_now is the index the engine keeps instead: the permanents it was printed on, filed as they entered, or every permanent while a row grants or copies one.

Trace A — Panharmonicon and Soul Warden

Panharmonicon (#1) and Soul Warden (#2) are on the battlefield under player 0. A 2/2 (#3) is put onto the battlefield from player 0's graveyard by one change_zone.

  1. execute_actionsstate the batch opens with one member, EnterBattlefield { object: #3, from: Graveyard } (trace seq 2).
  2. performlog two records: index 2 ZoneChange graveyard to battlefield, index 3 the entry (seq 6, 7). Neither carries a frame: an entry from a graveyard is no departure CR 603.10a frames for a battlefield ability.
  3. detect · the gatestate the window's kinds are ZoneChange and EnteredBattlefield. trigger_sources files Soul Warden under EnteredBattlefield, so it is a reader. Panharmonicon is no reader: it has no triggered ability.
  4. find_matchesboard candidates_now is [#2]. lists_before is empty (no batch removed an ability-list source, so there is no snapshot). push_live_candidates makes one Live candidate. No record carries a frame, so no departure_candidate.
  5. match_candidatesboard Soul Warden against record 2: refused, condition (seq 10, its arm reads entries). Against record 3: matched (seq 11). One match, from candidate 0.
  6. trigger_multiplier_candidatesstate no grant or copy flag, so trigger_multiplier_sources_now is the printed set, {#1}. One Live list for Panharmonicon; no snapshot survivors, no departures.
  7. additional_times_from(Panharmonicon, Soul Warden's match)board both on the battlefield. The ability is a static TriggerMultiplier that functions there (functions_as_static). abilities_of, "a permanent you control", reads Soul Warden through the list it matched through: controller 0, Panharmonicon's controller. The doubled arm (an entry) does not look back, and Panharmonicon's live list answers All, so it is on the board the arm reads. is_caused_by: Panharmonicon's event, an artifact or creature entering, asked of record 3 with Panharmonicon's own referents: a creature, so yes. The doubled arm names no act. +1.
  8. queue_matchesstate 1 + 1 = 2: two PendingTriggers with their own sequence numbers, the binding moved into the last (seq 12, 13: AbilityTriggered #0, #1).

The count leaves no record of its own: the second AbilityTriggered is the only sign of it in a trace. An emit point for the count would make step 7 a row.

Trace B — Gandalf dies beside a Golem

Gandalf the White (#1, legendary), a Golem (#2, an artifact creature) and the Mourner (#3, "whenever another creature dies, gain 1") under player 0. Gandalf and the Golem are destroyed by one batch of two Destroy members.

  1. execute_actions · capture_lkiframe before anything moves, each leaving permanent is framed as it is (CR 603.10a): Gandalf's frame walked fresh (seq 3), the Golem's a memo hit. The frames ride on the two departure records.
  2. performlog index 3: Gandalf battlefield to graveyard; index 4: the Golem (seq 8, 9). cleanup_zone_state takes Gandalf out of trigger_multiplier_sources: the set holds permanents, and Gandalf is a card in a graveyard now.
  3. find_matchesboard the Mourner is the one Live candidate. No snapshot: Gandalf's ability grants nothing to anything, so its leaving changes no survivor's list. Two departure_candidates, Gandalf's and the Golem's LastKnown lists, which carry no triggered ability and so add no rows to match.
  4. match_candidatesboard the Mourner's dies arm looks back. Its Live list answers All (it was there before and after, and no snapshot holds another list), so it answers for records 3 and 4: both matched (seq 12, 13). Two matches.
  5. trigger_multiplier_candidatesframe the printed set is empty now. But the window's departure frames are scanned for a multiplier, and record 3's frame carries Gandalf's: one LastKnown multiplier list.
  6. additional_times_from(Gandalf's frame, each match)frame a LastKnown list answers LookBackOnly; the doubled arm looks back, so Gandalf is on the board it reads, the one from before the event. is_caused_by asks Gandalf's event, a legendary permanent or an artifact leaving the battlefield, of each record, its subject read off the record's own frame (Gandalf the White's tenth ruling): record 3, a legendary creature, yes; record 4, an artifact creature, yes. +1 each.
  7. queue_matchesstate 2 + 2 = 4 (seq 14 to 17).

The arm decides the board, not the multiplier. Had the Mourner said "whenever a creature card is put into a graveyard from anywhere", an arm CR 603.6c says is not a leaves-the-battlefield ability, its arm would not look back, Gandalf's LastKnown list would not be admitted, and nothing would double it: Gandalf is not on the board after the event. With Gandalf still on the battlefield, the same arm is doubled (Gandalf's ninth ruling, gandalf_doubles_a_from_anywhere_trigger_on_a_legendary_creature_dying).

Trace C — the Granter dies

A 2/2 carrier (#1), a legendary Granter (#2) whose Layer 6 row gives the carrier Gandalf's multiplier for as long as the Granter is on the battlefield, and the Mourner (#3). The Granter is destroyed.

  1. execute_actions · departs_an_ability_list_sourcestate the Granter is the source of a row that grants an ability, so its leaving changes a survivor's list. The batch takes a LookBackSnapshot before it performs: look_back_frames holds the trigger candidates and, since TR-5g, the multiplier sources; the grant flag is on, so that is every permanent, the carrier among them, its list holding the granted multiplier.
  2. performlog index 3: the Granter to the graveyard (seq 6). The row ends with its source, and the registry summary's grant flag goes off.
  3. lists_beforeframe from the one snapshot, a list from before for each object still here: the carrier and the Mourner. The Granter has left and is a departure candidate instead.
  4. push_live_candidates(Mourner)board two candidates: the Mourner's Live list, marked as having a list in snapshot 0, and right behind it its Before list for snapshot 0.
  5. match_candidates · the Live listboard record 3 was performed by the snapshotting batch, so the Live list answers AllButLookBack: the dies arm looks back and is not admitted. Refused, condition (seq 9).
  6. match_candidates · the Before listframe the Before list answers LookBackOnly for record 3: matched (seq 10). This is the Mourner asked twice. On this board both lists hold the same trigger; on Humility's board they would not, and the one from before is CR 603.10's.
  7. trigger_multiplier_candidatesframe the flag is off and the printed set empty, so trigger_multiplier_sources_now is []. The snapshot's survivors that carry a multiplier are read too: the carrier's list from before has Gandalf's. push_live_candidates(carrier): its Live list (no multiplier now) and its Before list (the granted one).
  8. additional_times_from(carrier's Before list, the match)frame it answers LookBackOnly for record 3, and the arm looks back: on the board. The Mourner is "a permanent you control". The Granter, legendary, left the battlefield: is_caused_by holds. +1.
  9. queue_matchesstate 1 + 1 = 2 (seq 11, 12).

What review fixed here. Step 7 first read trigger_multiplier_sources_now alone, which is empty once the grant ends, so the count was 0 where the board from before has a multiplier. The audit, which treats every object as a candidate and a possible multiplier, counted 1 and failed the test. The fix reads the snapshot's survivors that carry one, the same reach find_matches gives a trigger.

What TR-5g changed, and the act rule

The count reads the dispatcher's own lists. match_candidates now says which candidate each match came from, so the count reads the trigger's source as it was matched: on the battlefield, or off its frame from it (Teysa Karlov's first and seventh rulings). The multipliers are read the same three ways, and on_the_board_read_by is the one test of whether a multiplier's list is on the board the matched arm reads: answered_arms and admits, the matcher's own. A snapshot holds the multipliers as well as the triggers, or step 7 of Trace C would have nothing to read.

The act rule (Teysa Karlov's fifth ruling: "whenever you sacrifice a creature" triggers once). The engine writes a sacrifice and the death it causes as one ZoneChange record whose act is Sacrificed, so the record matches Teysa's event, a creature dying, and the sacrifice arm too. What tells them apart is the arm: is_caused_by refuses when the doubled arm names an act (named_act) that the multiplier's own arm does not. The death the sacrifice caused is still doubled for "whenever a creature dies", which names none. named_act is an exhaustive match over every arm, so a new arm must say whether its record holds two events. Today only a zone change's act does: an entry and its zone change, a token's creation and its entry, are separate records, and so are separate events.

Why is_caused_by covers every event a multiplier can name. It does not have its own matcher. It asks the multiplier's arm of the record through triggering_events_in, the function every trigger arm is matched by, an exhaustive match over TriggerEvent and the record; a new arm cannot compile until it is matched there, and then multipliers read it too. The one rule of the count's own is the act rule above. The audit checks the rest: it counts again with every object a candidate and a possible multiplier, and the two counts must agree, every dispatch of every audited game.
