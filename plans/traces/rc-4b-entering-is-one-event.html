The map

Every entry is one proposal through one chokepoint. change_zone with a battlefield destination proposes an EnterBattlefield that carries where the card is coming from; no ZoneChange onto the battlefield is proposed any more, and building one is a debug assertion. The entry performer moves the card, announces the zone change, builds the entity and announces the entry. The frame the decide phase reads is unchanged from RC-4 and is now reached from two places: a filter-scoped AffectedSet asking whether the entering object matches, and gather's source 1a asking what abilities it has.

Two orders, on purpose. The state order is the CR's — stack from 601.2a, taps at 601.2g, cast at 601.2i — and the engine follows it. The log order is tap, move, cast, because the move is an event only once the cast is real. No ruling can tell them apart: a tap trigger and a cast trigger are both placed the next time a player would receive priority (CR 603.3), after the cast completes, in their controller's order (603.3b). What a reader cannot do is replay the state order from the log; the log is the trigger record, and the state is the state. Every completed cast in a fuzz game reorders this way — 703 in 40 performance games — which the phase plan's expected-divergence list did not anticipate.

Tracing the rest of the engine

This page was built by reading the code and the phase's tests and writing the walk down by hand — twice now. That is the right cost for a phase's close, and the wrong cost for a question asked mid-debugging. The plan has three tiers, each with a point on the critical path where it pays for itself; the first has started and the third is now unblocked.

Why those points on the critical path

  1. Tier 2 before item 6, not after. Trigger detection reads the performed-action stream, and the first question anyone will ask of the dispatcher is "why did this trigger, or not", which is a trace question about proposals, events and the frames they were judged against. Building the sink first means the trigger phase ships with its own explanation. Its seam with the entry-hop fix has now been used — execute_batch_inner and the entry performer are where RC-4b's emit points would go — and the remaining half of that seam, item 46's multi-entry batch, is RC-5 part 2, which is where the sink most naturally rides.
  2. Tier 3 after the entry-hop fix — which is to say, now. The fix changed the chokepoint's shape as predicted: the entry's move is in the entry performer, one emitter has three callers, and CLAUDE.md's bullets were restated. A map drawn against 6541d0b will stay true through RC-5, whose batch restructuring adds no arm.
  3. Tier 1 keeps going regardless. RC-5's page should show the batch-scoped frame deciding two entries against one board, which is the thing item 46 says is unreachable today. Item 7's page should show the dependency ordering choosing a non-timestamp order, which is the change that phase exists for. A page per phase whose examples are its findings is a better handoff than a findings list.

What not to do

Do not generate a page from every test: the point of a trace page is the two examples that carry the phase's idea, and eight hundred traces are a log, not an explanation. Do not draw diagrams of code that is about to change; the map waited for the hop fix for that reason. And keep every page pinned to a commit and the frozen CR version, as this one is, so a stale page says so on its first line.
