Control Is Announced by a Sweep

A trigger on a change of control looks back to the permanent as it was just before the change (CR 603.10d). But no action changes control: control is the layer walk's output (CR 613.1b), so a row starting or ending moves it and nothing proposes or announces that. TR-4d's answer is a sweep, announce_control_changes in engine/triggers/control.rs: at fixed moments it compares each permanent's controller with the one last announced, announces each difference, and looks back to a frame kept for that purpose. This page walks the three findings that decided how the sweep works: a steal that ends at cleanup, the first control row on a board, and Ray of Command's rows with no batch between them.

The map

Four words carry the page. A permanent's announced controller (PermanentState::announced_controller) is the controller the event stream last announced for it: the one it entered under, until a sweep announces a change. Its kept frame (PermanentState::frame_before_control_change) is the frame the next change of its controller looks back to. The gate decides whether a sweep walks anything: a control-changing row exists now (RegistryScopeSummary::any_control_changing), or one existed at the last sweep (GameState::control_effects_at_last_sweep). A keep (keep_frames_before_control_change) writes the kept frames just before something writes a row.

The sweep runs at fixed points, all through settle_layer_consequences (TR-5f's settlement, which runs it beside the type-change removal from combat and skips it while the layer epoch is where the last one left it): the head of an outermost batch outside a dispatch, the same batch's close while its window is open, each pass of perform_sba_and_triggers, and the cleanup step after CR 514.2's expiry. A batch's head is a sweep, so a batch needs no keep. The writes that happen outside a batch keep the frames themselves: a row a resolution writes (add_resolution_row), a static's registration (keep_frames_before_the_first_control_row), and the two expiries.

Why a sweep, and why the frames are kept. A "becomes" event fires on the transition only (CR 603.2e), and control has no performer whose transition could be watched, so the sweep detects the change where computed values are read again: it walks each permanent and compares. What it finds has already happened, so the frame from before has to exist already. While a control row exists the sweep walks every permanent anyway, so it keeps each frame it read for free. Control moves only when the board does (in a batch, in a resolution's row, in a static's registration, in an expiry), so a frame kept at the last of those moments is exactly the board "immediately prior to the event", not merely the board at the last sweep.

Trace A — a steal that ends at cleanup

The Fixture Betrayer (#21) is player 1's. Act of Treason resolves for player 0; the owner's trigger resolves; the test moves the turn to the postcombat main phase and lets the game run through the end of turn.

  1. the boardstate no control-changing row, so the gate is off. The Betrayer is announced under player 1 and has no kept frame.
  2. add_resolution_row(Layer2Control) · keep_frames_before_control_change(true)board Act of Treason's steal is the first control row on the board (Trace B's subject), so the keep walks every permanent and keeps the Betrayer as it is: controller 1 (the walk at epoch 24, seq 4). Then the row is written.
  3. execute_batch(Untap) · settle_layer_consequencesboard the untap is an outermost batch, and the epoch has moved, so its head settles. The gate is on. The Betrayer walks under player 0 (seq 5), its announced controller is 1: a change. The kept frame (controller 1) is handed back as the frame before, and the frame just walked becomes the kept one.
  4. announcelog record 1, ControlChanged 1 → 0 (seq 6), its lki built from the frame before: controller 1. Its window is its own and is dispatched now, before the untap's (CR 603.4's instant). The Betrayer's live list refuses (seq 7, condition); its list from before, out of the snapshot, matches (seq 8). The trigger's controller is the frame's, player 1 (CR 603.3a): the owner draws two.
  5. add_resolution_row(Layer6Ability) · keep(false)board the haste row. The gate is on, so the keep walks (seq 13, controller 0); nothing is waiting to be announced, and the Betrayer's kept frame equals its frame now, so nothing is written. The row is written after, so the kept frame has no haste.
  6. cleanup · keep_frames_before_control_change(false)board the cleanup step begins (record 10). Before CR 514.2 ends the "until end of turn" rows, the expiry keeps the frames: the Betrayer's frame now has haste, so its kept frame is written again, controller 0 with haste. Then remove_expired_at_cleanup removes both rows, and any_control_changing is false.
  7. settle_announced_controllersstate the cleanup step's settlement. No row exists now, but control_effects_at_last_sweep is true, since the last sweep ran with one: the sweep runs. With no row there is nothing to walk; a permanent's controller is the one it entered under, entry.controller, player 1. The announced controller is 0: a change. The flag goes false, so the next sweep is a no-op again.
  8. announceframe record 11, ControlChanged 0 → 1 (seq 60), its lki the frame kept in step 6: controller 0, haste. The live list refuses (seq 62) and the list from before matches (seq 63), for player 0: the thief lost control, and draws two (records 13 to 16).
  9. CR 514.3alog a trigger is waiting, so the cleanup step grants priority, and another cleanup step begins (record 18), as Ogre Geargrabber's fourth ruling and Ray of Command's third say.

With the gate's second half gone. The re-read's first defect: a gate on any_control_changing alone. The registry's summary is rebuilt as rows go, so at step 7 it says no, and the sweep returns at once. Run that way (the gate cut to if !rows in a copy of the crate), the cleanup step announces nothing, only one cleanup step begins, and the thief draws nothing. Worse, the Betrayer stays announced under player 0 while it walks as player 1's, and every later sweep on a board with no control row is gated off too, so the change is never announced. The flag was first control_announced_away; the review renamed it to what it asks.

Trace B — the first control row

A Fixture Banner (#21), player 0's, has a Layer 6 row giving "When you lose control of this creature, draw a card" to the creatures its controller controls. Grizzly Bears (#22) is player 0's. Nothing has changed control. Act of Treason resolves for player 1.

  1. the boardstate no control row, so the gate is off: no sweep has walked anything, and no permanent has a kept frame. The Bears has the granted trigger, under player 0.
  2. add_resolution_row(Layer2Control) · keep_frames_before_control_change(true)board sets_controller is true, since the row about to be written is a control row, so the keep runs with the gate off. It walks every permanent in battlefield_ids_ordered order and keeps each frame: the Bears' is controller 0, with the granted trigger (the probe's print of the kept frame).
  3. the row is writtenboard the Bears walks under player 1 now, and without the trigger: the Banner gives it only to its own controller's creatures.
  4. execute_batch(Untap) · the sweepframe the head's sweep finds the Bears' change, 0 → 1, and hands back the frame kept in step 2. Record 2, ControlChanged (seq 4), its lki controller 0 with the trigger.
  5. match_candidatesframe the Bears' live list has no such trigger, so nothing is refused; its list from before matches (seq 5) for player 0, who draws a card. CR 603.10's "the existence of those abilities ... immediately prior to the event" is the kept frame.

The other site. The same board, with the steal written by a static instead: a probe fixture, "Fixture Usurper", an enchantment with "You control all creatures", put onto the battlefield from player 1's hand by change_zone.

  1. execute_batch(EnterBattlefield) · headstate the entry is an outermost batch; its head's settlement finds the gate off and walks nothing.
  2. keep_frames_before_the_first_control_row(Layer2Control)board as the Usurper's static registers its Layer 2 row inside the entry, no control row exists yet, so it keeps every frame first: the Bears at controller 0, with the trigger. A later control row registered inside a batch keeps nothing here, since that batch's head swept with the gate on.
  3. execute_batch · closelog the batch's close settles while its window is open, so record 4, ControlChanged 0 → 1 (seq 11), joins the entry's window (batch 0) after records 2 and 3, the entry's own. The list from before matches (seq 14), and player 0 draws.

With no keep before the first row. The re-read's second defect: a frame kept only while a control row exists holds nothing when the first row is written, and the first row is the common case, Act of Treason on a board with no steal in progress. Run with add_resolution_row's keep passing false, a debug build stops in announce: "#22's controller changed with no frame kept from before it", the assertion that names a site that writes a row without keeping. A release build falls back to the frame now: the record's lki is controller 1 with no trigger, nothing triggers, and nobody draws.

Decision 1 at TR-4d's design (the owner's): keep the frames at the two places that can write the first control row, a resolution's Layer 2 row and a printed or copied static's registration (a granted static cannot write one, since layers 1–5 refuse a grant). The alternatives were reading the first change off the board now with "you" taken from the record's from, which is wrong where the change moves a "you control" grant, as on this board; and refreshing the frames at every sweep point on every board, a walk of every permanent at every batch head in every game.

Trace C — Ray of Command, with no batch between its rows

The Fixture Betrayer (#21) is player 1's. Player 0 casts Ray of Command (#22) at it: "Untap target creature an opponent controls and gain control of it until end of turn. That creature gains haste until end of turn. When you lose control of the creature, tap it." Its order is not Act of Treason's: the untap comes first.

  1. cast_spelllog records 1 to 3: the cast, the targeting, SpellCast. The Betrayer's trigger refuses the cast's record (seq 7).
  2. resolve · Untapstate the untap is a batch (batch 1, seq 12 to 14). Its head settles with the gate off: no control row exists yet. The Betrayer is untapped, so nothing is performed.
  3. resolve · Remember(GainControl) · keep(true)board the steal's row is the first control row, so the keep runs: the Betrayer kept at controller 1, its frame from epoch 28 (seq 11's walk, served again by the memo). The row is written, and the epoch moves to 29.
  4. resolve · GrantKeywordFlag(Haste) · keep(false)board the gate is on now, so the keep walks: the Betrayer under player 0 (seq 15), its announced controller still 1. A change is waiting to be announced, and it looks back to the frame kept before it, so the keep returns and writes nothing. The haste row is written.
  5. resolve · CreateDelayedTriggerlog record 4 (seq 16), the delayed "When you lose control of the creature, tap it". A registration in the delayed-trigger registry, not a continuous effect: no row, and no keep. So the resolution wrote three things with no batch between them, and two of them were rows.
  6. the spell to its graveyard · headframe Ray of Command's own move is a batch (batch 3), and its head's sweep (seq 18) finds the change, 1 → 0. Record 5 (seq 19), its lki the frame from step 3: controller 1, no haste, the trigger.
  7. match_candidatesframe the Betrayer's live list refuses (seq 20) and its list from before matches (seq 21), for player 1, who draws two. Ray's delayed trigger is asked of record 5 too and refuses (seq 22): player 0 gained control here and lost none.

With the waiting change ignored. The build met this one: a row written after a change and before any batch. Run with the check removed, step 4 writes the frame it walked, the Betrayer just after the steal (controller 0; no haste yet, since the keep runs before its row). Record 5's lki then names player 0, both lists refuse, and nobody draws: CR 603.3a would make the thief the trigger's controller, and the thief did not lose control. Act of Treason never meets this: its untap comes between the steal and the haste, so the untap's batch head announces the change (Trace A, steps 3 and 4) before the haste row's keep runs, and that keep finds nothing waiting.

What TR-4d changed, and what came after

Before TR-4d nothing announced a change of control. ControlChanged had no writer: a steal was a row in the registry and a different answer from the next layer walk, and a trigger on it had nothing to match. TR-4d made the change an event the way CR 603.2e's "becomes" events are: detected on the transition, where the computed value is read again, with its own cause, GameRule::ControlChanges, since the sweep cannot tell which effect moved control. The changes one sweep finds are one event, so a "whenever an opponent gains control of a permanent from you" watcher stolen beside another triggers once for each (Zidane, Tantalus Thief's first ruling; a_watcher_stolen_with_another_permanent_triggers_for_each).

What the snapshot holds. Every permanent's kept frame, not only the changed ones': "creatures you control have ..." follows its source to the thief, and the creatures left behind lose what it gave them (a_grant_the_steal_moves_still_triggers_the_creatures_left_behind). The review round replaced a first build's pairing of two frames with this; a list the change left alone answers the same before and after, so the answer is the same by construction.

Since TR-5f the sweep is the first half of settle_layer_consequences, gated on the layer epoch, and it runs at a batch's close as well as its head, so a change a batch causes is announced in that batch's window (Trace B's static board). Since #278 (item 185), --audit re-walks every permanent after each sweep and requires its controller to be the one announced, whether or not the gate let the sweep walk (audit_announced_controllers; plans/elisions.md, the control sweep's row), and the dispatch audit matches the change's window against a snapshot of every object that could trigger, each as it was before the change (audit_frames_before_control_change).

Not walked here, because they are records that carry their own frames and are read the way TR-1's page reads a departure: a countered spell's frame with its stack entry (Lki.entry, item 253), a player's loss and the loser's departures (CR 603.9, 603.10f), and the two mill records (items 131 and 258).
