Applying an Entry Can Move the Board

Until RC-5 a Rewrite was a pure function of the event: the CR 616.1 loop decided what would happen and nothing happened while it decided. CR 614.13 says otherwise — an effect that modifies how a permanent enters the battlefield may cause other objects to change zones — so applying one is now a prompt and a mutation, in the middle of deciding an entry that has not happened yet. Four boards, walked one call at a time, with every read labelled by what it consulted: the board as it is, the permanent as it would be, the batch's own exclusion sets, or a player.

A · Devour: choose, move, count

Board A. The Elder returns from the graveyard with two creatures on the battlefield under the same player, and its controller sacrifices both. It arrives as a 7/7. The three things §9 said did not exist are steps 12, 16 and 18.

  1. 1GameState::change_zoneactions.rs:496to: Battlefield, cause: Returnedboard

    Reads the object's current zone — Graveyard — and routes a battlefield destination to the entry proposal. No ZoneChange { to: Battlefield } exists any more; constructing one is a debug assertion (RC-4b).

  2. 2default_enter_controllergame_state.rsboard

    No resolution is in flight, and the card is not a land drop, so CR 110.2b's default is the owner. That value is the proposal's controller and becomes CR 614.12's "under whose control it would enter" for everything below.

  3. 3propose_entryactions.rs:889board

    default_enter_mods seeds CR 306.5b's loyalty — none here — and strip_prohibited_counters asks CR 614.17d of the seed. The proposal is EnterBattlefield { object, from: Graveyard, controller, mods: NONE, cause: Returned }.

  4. 4execute_actions → execute_batch_inneractions.rs:294, 343RC-5scope

    Phase 1 begins. The outer entry_selection is taken and saved; entering is filled from the batch's EnterBattlefield members — here, the Elder alone. CR 614.13a is decided before any replacement is applied, because it is a fact about what is entering, not about what has entered.

  5. 5apnap_batch_orderactions.rs:435board

    One member, so CR 101.4's ordering has nothing to sequence. It still runs: the answer being trivial is not the same as the question not being asked.

  6. 6apply_replacementspipeline.rs:103CR 616.1 loop, iteration 1—

    Fresh applied / declined sets. Nothing has happened yet; the loop is deciding what the event is.

  7. 7EntryFrame::newlookahead.rs:49frame

    Built from the proposal, lazily. It answers for one object — the Elder — and for nothing else. Because it is built inside phase 1, the board it reads is the board before any member of this batch was performed.

  8. 8is_prohibitedrestriction/mod.rsCR 614.17d, on the frameframe

    No "can't enter" applies. A CR 101.2 prohibition would win here, ahead of the pipeline, and the entry would simply not happen (CR 614.6) with the card left in the graveyard.

  9. 9gathergather.rs:138frameboard

    Source 1a reads the Elder's effective ability list through frame.frame_of(object) — the card is still in the graveyard, so a plain walk would find nothing filter-scoped (RC-4b finding 1). Devour is AffectedSet::SourceOnly, which is CR 614.12's first sentence. The battlefield sweep finds nothing; the two Bears have no replacement abilities.

  10. 10forced_bucketgather.rs:755—

    One candidate, so CR 616.1a–e has one bucket with one member. No prompt: the rule chooses only among two or more.

  11. 11order_invariant_entry_bucketpipeline.rs:343RC-5

    Not consulted — the bucket has one member. It would refuse this bucket anyway: an EnterAfterMoving is not an EnterWith, and its application is neither commutative nor free of consequences.

  12. 12apply_rewrite → apply_auxiliary_movepipeline.rs:566, 867RC-5

    The first thing §9 said did not exist. apply_rewrite now takes &mut GameState, and only for this arm. Every other rewrite is still a pure function of the event; this one is CR 614.13's own statement that applying an entry replacement may change the board.

  13. 13auxiliary_candidatespipeline.rs:937from: BattlefieldRC-5scopeboard

    Three filters in order. Scope: entry_selection.admits — the Elder is in entering, and it is not on the battlefield either, so 614.13a costs nothing here and everything in trace B. Board: permanent_matches_filter over battlefield_ids_ordered, which is where "creatures you control" lives, because control and ownership diverge on the shared zone. CR 101.2: is_prohibited on the ZoneChange this choice would produce — a creature that can't be sacrificed is removed from the list, not offered and then refused.

  14. 14ask_choose_auxiliary_zone_changeask.rs:778bounds (0, 2)RC-5player

    The floor is zero, and that is devour's "you may": "any number" includes none, so declining is a count rather than a second prompt. Marking the def optional instead would ask twice and let a decline spend CR 614.5's one opportunity for a reason the card does not have. Unlike ask_choose_replacement this is asked with one candidate — take it or not is a real choice.

  15. 15entry_selection.chosen.extendpipeline.rs:867RC-5scope

    Recorded before the moves. Two reasons, and both have teeth: a nested batch takes and restores the scope, so a later write would be lost inside it; and codebase-state.md item 40 wants the outcome-bearing state on GameState before the next prompt, so a fork at that prompt sees it.

  16. 16execute_actions_new_batchactions.rs:322// AUXILIARY-MOVE:RC-5

    The second thing that did not exist. §4.2's default is that a nested execute_actions joins the enclosing batch, on CR 120.3f's grounds — lifelink's life gain is a result of the damage. These moves are the converse: performed while the entry is still being decided, before the entry event exists at all. Joining would hand a CR 603.2c "whenever one or more creatures die" one event where two devour creatures entering together have two.

  17. 17apply_replacements ×2pipeline.rs:103nested phase 1board

    Each sacrifice is a real trip through the pipeline with a fresh applied set (CR 614.5): a finality counter still exiles instead, Kalitas still gets its Zombie. The two moves are decided against one board and performed together — CR 701.21's simultaneity, which is why this is one execute_actions and not a loop.

  18. 18performed.len()pipeline.rs:867RC-5

    The third. Devour counts what was sacrificed, and CR 701.21a makes a sacrifice a move — so a move a replacement dropped (CR 614.6) was not one, and a move some effect redirected still was. Two moves performed × 3 = six +1/+1 counters, as an EnterMods.

  19. 19strip_prohibited_counterspipeline.rs:767frame

    CR 614.17d, asked of the counters as the AddCounters event CR 122.6 says they are, against the Elder's frame with the mods applied so far. A Solemnity or a Melira refuses them and the entry goes on without them.

  20. 20EnterMods::mergetypes/replacement.rs—

    CR 616.1f's accumulation, unchanged. The loop re-gathers against the rewritten event, finds devour already in applied (CR 614.5), and returns.

  21. 21execute_batch_inneractions.rs:343RC-5scope

    Phase 1 ends and the scope is restored — the exclusions belonged to these simultaneous entries, and phases 2 and 3 are past deciding. Phase 2 performs the decided entry.

  22. 22perform_action → place_on_battlefieldactions.rs:780, game_state.rs:682board

    The move from the graveyard, the ZoneChange event, the entity, its CR 613.7 timestamp, six counters with one CR 613.7c timestamp, then PermanentEnteredBattlefield. The counters are on before anything can observe the permanent, so a 1/1 is never seen as a 1/1.

batch 7 ZoneChange Bears#1 Battlefield → Graveyard [Sacrificed] batch 7 ZoneChange Bears#2 Battlefield → Graveyard [Sacrificed] batch 6 ZoneChange Elder Graveyard → Battlefield [Returned] batch 6 CountersChanged Elder +1/+1 +6 batch 6 PermanentEnteredBattlefield Elder

Read the batch ids, not the order. The sacrifices are performed first and belong to a batch opened after the entry's — the entry's batch is still open, deciding. That inversion is the shape CR 614.13 has: the moves happen while the entry is being decided, and they are not part of it.

B · The same object twice, and where CR 614.13b actually bites

Board B. One Bear, and a second CR 614.13 effect — a filter-scoped "exile any number of creature cards from your graveyard" — applying to the same entry. Devour applies first and puts the Bear into the graveyard; the second effect then enumerates that graveyard.

This is the phase's finding, and a mutation pass produced it. The first draft of RC-5's tests asserted CR 614.13b with two devour effects, which is the CR's own example — and deleting the chosen set did not break them. With both effects reading the battlefield, a sacrificed creature stops matching the next filter on its own, so the rule looks like bookkeeping. It is not: the moment two effects' zones chain, the same object is a legal candidate twice and only 614.13b refuses it.

  1. 1–9as trace A—

    Same route to the CR 616.1 loop. gather now finds two candidates: Grave Chain's filter-scoped effect from the battlefield sweep, and the Elder's own devour, spliced in after it — CR 613.7's oldest-first, and the entering permanent is the newest object there is.

  2. 10order_invariant_entry_bucketpipeline.rs:343RC-5

    Refused: neither member is an EnterWith. The prompt is real, and the CR's own example says why — the Elder ends with three counters or with five, depending on which applies first, and never with eight.

  3. 11ask_choose_replacementask.rsCR 616.1player

    Index 1 — devour first.

  4. 12apply_auxiliary_movepipeline.rs:867scopeplayer

    Candidates: the one Bear. Chosen; chosen := [Bear]; the nested batch moves it to the graveyard. The Elder is a 4/4-to-be.

  5. 13apply_replacementspipeline.rs:103CR 616.1f, iteration 2frame

    Re-gathered against the rewritten event. Devour is in applied; Grave Chain is not, and still applies. One candidate, so no CR 616.1 prompt.

  6. 14auxiliary_candidatespipeline.rs:937from: Graveyardscopeboard

    The graveyard now holds the Bear and the Elder, and both are creature cards matching the filter. Both are refused, by different clauses of the same rule: the Elder by entering (614.13a — it is the object that will become the permanent), the Bear by chosen (614.13b — it was already chosen to change zones while applying a replacement to this entry). Zero candidates.

  7. 15ask_choose_auxiliary_zone_changeask.rs:778—

    Not called. The empty candidate list is skipped before the ask, not answered by it — which is what makes "no third prompt" the assertion the test can make, and a ScriptedDecisionProvider with an empty queue the sharpest way to make it.

What the two clauses cost if either is missing. Without entering, the Elder exiles itself as it enters and never arrives. Without chosen, the Bear is sacrificed and then exiled — one object, two zone changes, from replacement effects applying to one entry, which is the sentence CR 614.13b is. Both mutations are in the phase's mutation pass and both are killed by this trace's test.

C · Whose power? frame_of(source) and the asymmetry

Board C. An Elvish Lord returns from the graveyard while Master Biomancer — a 2/4 Elf — is on the battlefield. The Lord enters with two counters, not three.

  1. 1–8as trace A—

    Through change_zone to the CR 616.1 loop, with the frame built from the proposal.

  2. 9gather → set_affectsgather.rs:138, 480frame

    The Biomancer's AffectedSet::Filter is matched against the Lord through permanent_matches_filter_in_frame: it is a creature, and its controller is the proposal's. "Each other creature you control" needs no filter leaf — the Biomancer's own ability can never reach a Biomancer that is entering, because the sweep reads the battlefield and source 1a admits only SourceOnly.

  3. 10order_invariant_entry_bucketpipeline.rs:343RC-5

    One member here, so nothing is suppressed. With a second EnterWith beside it the premise matters: an amount is order-invariant if it is Fixed, or its source is not the entering object — because only then can frame_of return Some. Exact rather than conservative, so a Biomancer keeps the suppressed prompt and the fuzz pool keeps its zero-prompt property.

  4. 11apply_rewrite → evaluate_enter_templatepipeline.rs:566, 808RC-5

    The template's amount is AmountExpr::SourcePower. EnterMods was the payload of both the definition and the event, and §3.2 recorded that as a virtue; it held exactly as long as every amount was a literal, because the event's mods must be numbers the performer can put on.

  5. 12EntryFrame::frame_of(source)lookahead.rs:79frame

    None. The frame answers for one object and the source is not it. That single line is the whole of §5b's asymmetry: one object is hypothetical, nothing else is.

  6. 13get_effective_power(game, source)characteristics.rs:238board

    2. A full layer walk of the Biomancer on the real board, where the Lord is not a permanent and CR 604.3 keeps its anthem from functioning. Not the printed 2 either — an anthem on the Biomancer would make this 3, and the test asserts both directions.

  7. 14place_on_battlefieldgame_state.rs:682board

    Two counters. And the moment the Lord is a permanent its anthem does reach the Biomancer, which is now a 3/5 — the two answers really are different, which is what makes the assertion mean something.

The counterfactual, in one line. Read frame_of(entering) instead of frame_of(source) and the Lord gets three counters: the frame has the Lord's own anthem in it (clause 2), and the anthem pumps Elves, and the Biomancer is an Elf. That is the mutation, and it is killed by this trace's test.

D · Two entries, one board — what RC-4b already paid for

Board D. Two Master Biomancers entering as one execute_actions batch. Each gives the other nothing. §9 scheduled this as RC-5's second piece and sized it at ~400 lines in execute_batch_inner; the re-size found it already true.

  1. 1execute_batch_inneractions.rs:343scope

    entering := [Biomancer A, Biomancer B]. Phase 1 begins.

  2. 2apply_replacements(A)pipeline.rs:103board

    The battlefield sweep finds no Biomancer: B is in the graveyard, not on the battlefield, and its static ability functions only there (CR 604.3). Source 1a finds A's own ability and refuses it — the sweep is for other objects, and 1a admits only SourceOnly, which "each other creature you control" is not. No candidate. A enters with nothing.

  3. 3apply_replacements(B)pipeline.rs:103board

    The step the old §9 got wrong. It claimed B would be decided after A was performed and would see it on the battlefield. Phase 2 has not run: nothing has been performed. A is still in the graveyard. B enters with nothing too.

  4. 4phase 2actions.rs:343board

    Both entries are performed, in batch order. Their CR 613.7 timestamps are allocated one after another — which is allocation order, not CR 613.7m's APNAP order, and is the one thing item 46 still owes. Same controller here, so any order is that player's choice and 613.7m is satisfied trivially.

What §9 said this piece would cost, before the re-size
RC-5 piece 2 — the batch-scoped frame (§5b) "Today an entry is proposed inside the zone change's performer (RC-2's nested propose_entry), so the second member of a [ZoneChange, ZoneChange] batch is decided after the first was performed and sees it on the battlefield." Sized: ~400 in execute_batch_inner and perform_action's ZoneChange arm. Measured against the tree, 2026-09-03: every clause false. change_zone routes a battlefield destination to propose_entry; a ZoneChange { to: Battlefield } proposal is a debug assertion; phase 1 decides every member before phase 2 performs any. Paid by RC-4b's +378 / -250.

What is honestly left is not a frame question: nothing produces a multi-entry batch. propose_entry is called once per entry, CreateToken loops it, and Primitive::ReturnToBattlefield is a stub — so this trace is built by calling execute_actions directly, and the test that carries it says so. The producer is codebase-state.md item 46, sized there for the first time at ~350 lines and a card, because a mass return needs a graveyard leaf on SelectionFilter and item 48's controller field before it can exist.

What this page does not show, and where it went

  1. CR 613.7m. "Before card breadth" item 4 named CR 614.13's auxiliary zone changes as one of the two things that make APNAP timestamps reachable. They are not: an object receives a timestamp in one production place, place_on_battlefield, and devour's moves are battlefield → graveyard while Sutured Ghoul's are graveyard → exile. Neither is an entry. 613.7m stays with CreateTokens in Phase RE, beside item 52's token residual.
  2. Sutured Ghoul's power and toughness. The card is registered for its exile clause; its */* reads "the exiled cards", which CR 614.14 links to the exiling ability — CR 607, ticket T20, the same thing Painter's Servant waits on. A Ghoul that exiles something should live and dies instead, which is a missing CDA rather than a wrong one.
  3. Master Biomancer's Mutant clause. A type an entry modification adds is a field EnterMods does not have, and adding one fires item 47's expiry condition (a): ByType and BySubtype would stop being mods-invariant and every entry bucket would prompt. It also wants a Layer 4 effect with somewhere to live after the entry.
  4. A production multi-entry batch, which is trace D's honest gap and item 46's remaining half.
